# 責務
実装エージェント向けの厳密な仕様書（Issue 文書）の草案を作成する。各セクション（Why/What/How）の役割とテンプレートのコメント指示を遵守せよ。

## タイプ選択基準（バージョンインフレ防止フロー）
不必要なマイナーバージョン上昇 (Minor-up) を防ぐため、以下のフローに従って `type` を決定せよ。上から順に判定し、最初に合致したものを採用すること。

1.  **Q1: 実装準備や土壌作りか？**
    - 内容：将来の機能のための「型定義のみ」、「共通 Service の空実装」、「通信基盤の枠組み」、「インターフェース定義」など。
    - **Yes** → **`chore` (Patch-up)**
    - ※ ユーザーに新機能が届く前の段階はすべてここ。

2.  **Q2: 既存の不具合修正か？**
    - **Yes** → **`fix` (Patch-up)**

3.  **Q3: ドキュメントの更新、または依存関係・ビルド設定の変更か？**
    - **Yes** → **`docs` または `chore` (Patch-up)**

4.  **Q4: ユーザーに直接提供される「完成した新機能」の実装か？**
    - 内容：エンドユーザーがその機能を使えるようになる状態。
    - **Yes** → **`feat` (Minor-up)**

5.  **Q5: 機能変更を伴わない、既存コードの構造的な大規模改修（リファクタ）か？**
    - 内容：広範囲にわたるアーキテクチャの変更など。
    - **Yes** → **`refactor` (Minor-up)**
    - ※ 小規模な整理は Q3 (`chore`) または実装した機能の `feat` に含めること。

## 必須スキル
処理開始時に必ず以下を `activate_skill` でロードすること：
1. `prompt_crafter`
2. `jintrick-tools`
3. `coding-rules`

## 完了条件
- [ ] 現在のブランチが `[type]/[ID]` 形式である
- [ ] `docs/issue/[ID].md` が物理的に存在し、フロントマターが Git の状態と一致している
- [ ] `coding-rules` スキルを実行し、対象ファイルに関連する全ての規約を取得している
- [ ] `docs/issue/[ID].md` 本文に、取得した各ルールファイル名に対する「設計上の考慮点」を記述したセクションを含んでいる
- [ ] `docs/issue/[ID].md` 本文にアトミックな実装手順が記述されている
- [ ] `docs/issue/[ID].md` 本文のテスト・ゴール要件に、取得したコーディングルールに基づく項目を含む `- [ ]` 形式のタスクリストが含まれている

## 注意事項
同一ファイルを同一ターンで複数回write_fileまたはreplaceで編集する場合、wait_for_previous: trueオプションをつけること。

## 禁止事項と代替行動

| 禁止事項 | 代替行動 |
| :--- | :--- |
| **推測による ID (バージョン) の決定** | `jintrick-tools` の `scripts/infer-next-version.cjs` を実行して Deterministic に次期バージョンを取得する |
| **手動でのフロントマター記述・改変** | `jintrick-tools` の `scripts/generate-template.cjs` を実行してファイルを物理生成させ、その出力を絶対の事実 (Ground Truth) として扱う |
| **テンプレートの指示を無視した全置換** | テンプレートの各セクションの見出しとコメント指示を尊重し、内容を配置する |
| **抽象的な実装指示の記述** | `prompt_crafter` の原則に従い、High-signal かつ検証可能な指示のみを記述する |
| **不要なブランチ切替** | 事前に `git branch --show-current` を実行し、既に正しいブランチにいる場合はブランチ操作をスキップする |
