# Issue: システムプロンプト改修による PowerShell 5.1 環境での Linux コマンド競合問題の解決

## 背景と問題点
本プロジェクトの実行環境は Windows / PowerShell 5.1 である。
しかし、AI エージェントが Linux/Unix 形式のコマンド（`find`, `ls -la`, `rm -rf` 等）を無意識に使用してしまうことがあり、名称衝突（Windows 標準バイナリ `find.exe` 等との競合）や PowerShell エイリアスによる引数エラーが発生し、タスクの失敗や意図しない動作を招くリスクがある。

## 解決策
システムプロンプト（`skills/gemini-cli-expert/references/system_prompts/v0.35.3/jintrick.md`）を直接改修し、エージェント自身の根本的な行動規範として、PowerShell 5.1 環境におけるコマンド実行のルールを明記する。
※ Hook 等による事後検知ではなく、プロンプトによる事前制御（行動の修正）を行う。

## 実装内容詳細
`skills/gemini-cli-expert/references/system_prompts/v0.35.3/jintrick.md` の `## Tool Usage` セクションにおいて、以下の **Compressed Instruction (圧縮命令)** および拘束条件を追記・編集する。抽象的な注意喚起（「気をつける」等）は一切禁止する。

1. **環境拘束 (Environment Constraint)**:
   - 実行環境が `Windows PowerShell 5.1` であることを明記する。
   - 例: "The execution environment is strictly Windows PowerShell 5.1."

2. **禁止事項と代替行動の定義 (Prohibited Actions & Fallbacks)**:
   以下の制約を列挙し、違反時の代替手段をセットで明示する。
   - **ファイル操作・検索 (File Operations & Search)**: シェルでの `cat`, `grep`, `find`, `sed`, `awk` の使用を禁止する。代替として、必ず **提供されているAIツール (`read_file`, `write_file`, `grep_search`, `glob`, `replace`) を最優先で使用する** ことを強制する。
   - **引数非互換 (Argument Incompatibility)**: `ls -la`, `rm -rf`, `cp`, `curl -L`, `wget -O` などの使用を禁止する。シェル実行が必須な場合の代替として `Get-ChildItem`, `Remove-Item -Recurse -Force`, `Copy-Item`, `Invoke-WebRequest` を指定する。
   - **名称衝突 (Name Collision)**: `sort` の使用を禁止する。代替として `Sort-Object` を指定する。
   - **構文エラー (Syntax Error)**: `&&` 演算子の使用を禁止する。代替として `;` または `if ($?) { ... }` を指定する。
   - **環境変数 (Environment Variables)**: `export VAR=value` 形式を禁止する。代替として `$env:VAR="value"` を指定する。
   - **存在しないコマンド (Missing Commands)**: `which` の使用を禁止する。代替として `Get-Command` を指定する。

3. **同期プロトコル (Synchronization Protocol)**:
   - `jintrick.md` 編集後、必ず `ORIGINAL/INTENT` の形式を保持し、差分を最小化する。
   - `node tools/jintrick_to_system.cjs` を実行し、`.gemini/system.md` への反映を確定する。

## Appendix: 技術的選定理由 (Why/Why Not)
当初、コマンドの誤用を防ぐために Hook（Linter）を実装し、実行時にブロック・修正するアプローチを検討した。しかし、本件のような「環境の根本的な前提（Windows PowerShell であること）」は、AI の振る舞いの土台を成すものであり、事後的に Hook で修正するよりもシステムプロンプトによる事前制御（行動の根本修正）が相応しいと判断した。また、`prompt_crafter` の原則に基づく高密度な拘束条件を用いることで、システムプロンプトの記述だけでも十分な効果が得られると期待できる。
