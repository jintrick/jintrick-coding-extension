# Issue: 通知フックの拡張（ask_user 待機状態への対応）- 技術的敗北の記録

## 概要
エージェントが `ask_user` で待機する際、Windows による通知抑制を回避し、即座にトーストを表示させることを試みた。

## 背景と問題点
思考時間が長いタスクにおいて、ユーザーが画面を見ていない場合の停滞を防ぐため。

## 結論：技術的制約による実装断念
複数の検証（AppID 偽装、Priority: High、Alarm Scenario、Start-Process によるプロセス分離、早期リターン等）を重ねたが、Gemini CLI が `ask_user` で入力を待機している（Raw モードでターミナルを専有している）間、Windows OS は当該セッションに紐付く全てのトースト通知ポップアップを物理的にロックすることが判明した。

通知は OS のバックグラウンド（通知センター）には登録されるが、画面へのトースト表示はユーザーが `ask_user` に回答し、ターミナルの排他的ロックが解除された瞬間にまで遅延する。回答後の通知はユーザーにとって「ノイズ」でしかないため、本機能の導入は見送る。

## 得られた知見
- **AppID 偽装**: `Microsoft.Windows.Explorer` を使用することで、一部の通知抑制を回避できる。
- **Alarm Scenario**: `scenario="alarm"` 属性により、集中モード等を貫通できる。
- **プロセスの壁**: CLI が対話待機状態にある間は、OS レベルで UI イベント（トースト）のレンダリング順序が制御され、外部からの割り込みが著しく困難である。

## 今後の対応
本 Issue で得た「通知の貫通力を高める手法」を、既存の完了通知（`AfterAgent`）の強化に転用する（v2.5.1 へ継続）。
