# Issue: 既存の通知フック (toast_notification_hook.cjs) の強化：NotificationイベントおよびBeforeToolイベントへの対応

## 背景と問題点 (Why)
Gemini CLIがツール実行の承認を待つ際や `ask_user` 等の入力を待つ際、ユーザーが別ウィンドウで作業していると進行停止に気づかず、開発効率が低下する。
現在の `toast_notification_hook.cjs` は長時間タスクの完了（`AfterAgent`）のみを通知対象としており、対話待ちの状態を検知して通知する仕組みが不足している。

## 解決策 (What)
`toast_notification_hook.cjs` を拡張し、`Notification` (ToolPermission) および `BeforeTool` (ask_user等) イベントをトリガーとしたデスクトップ通知機能を追加する。
通知配信ロジック（`spawnSync` および物理ファイル生成方式）は、過去の最適化で得られた堅牢性を維持するため変更せず「聖域」として扱う。変更は「イベントの捕捉（When）」と「メッセージの選択（What）」に限定する。

## 実装内容詳細 (How)

### 1. 設計上の考慮点 (Design Considerations)
対象ファイル: `hooks/scripts/toast_notification_hook.cjs`
- **comment-preservation.md**: `deliverWindowsToast` 内の `AppID ('Microsoft.Windows.Explorer')` 指定や `Priority ('High')` 設定の背景コメントを「聖域」として一切削除せず維持すること。
- **no-temp-files-in-root.md**: 一時ファイル（`.ps1`, `.lock`）は引き続き `os.tmpdir()` を使用し、`spawnSync` 完了後に確実に削除する既存の安全策を維持すること。

### 2. 技術的根拠
- `BeforeTool` はツール実行「前」に同期実行されるため、既存の `spawnSync` を維持しても CLI の Raw モード（UIロック）に入る前に通知を完了できる。
- 非同期化（detached）による不確実性（プロセスの浮遊、クリーンアップ失敗のリスク）を排除し、同期実行のまま要件を実現する。

### 3. アトミックな実装手順
1. **フック定義の更新 (`hooks/hooks.json`)**:
   - `Notification` セクションを追加し、`matcher: "*"` で `toast_notification_hook.cjs` を指定。
   - `BeforeTool` セクションに `toast_notification_hook.cjs` が含まれていることを確認（既存の計測ロジック用）。
2. **フックロジックの拡張 (`hooks/scripts/toast_notification_hook.cjs`)**:
   - `showToast` 関数を `showToast(cwd, message, session_id)` に拡張。
   - `processEvent` 内で以下のイベントを捕捉し、適切なメッセージを `showToast` に渡す：
     - `Notification` かつ `notification_type === 'ToolPermission'` の場合 → 「実行の承認待ちです」
     - `BeforeTool` かつ対象ツール（`ask_user` 等）の場合 → 「入力を待機しています」
     - 既存の `AfterAgent` (長時間タスク) の場合 → 「タスク完了: 実行時間 X.Xs」

## ゴール
- `run_shell_command` 等の承認待ち発生時に「実行の承認待ちです」という通知が表示される.
- `ask_user` 等の入力待ち発生時に「入力を待機しています」という通知が表示される.
- 既存の「長時間タスク完了通知」が正常に動作し続ける.
