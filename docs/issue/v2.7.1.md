# Issue: github-investigator スキルのトリガー精度向上と規約強制の強化

## 概要
`github-investigator` スキルが、GitHub 調査の際にエージェントによって自律的かつ確実に応用されるよう、`description` をセマンティック・ルーティングに最適化し、さらに `SKILL.md` 内での規約強制力を強化する。

## 背景と問題点
前回の実装では `description` が単なる機能説明に留まっており、エージェントが GitHub 調査のタスクとスキルの関連性を即座に認識（トリガー）する力が弱かった。また、スキルがロードされた後も、エージェントが従来の「簡易的な検索・要約」という古い習慣に戻ってしまうリスク（規約の軽視）が残っていた。

## 解決策
1.  **セマンティック・ルーティングの最適化**: `description` に具体的なトリガー（`gh` コマンド名、ファイル操作の文脈）と、解決すべき具体的なリスク（ラベルの誤認、メンテナ合意の欠如）を明示し、ベクトル空間での関連性を高める。
2.  **規約の強制化 (Critical Rules)**: `SKILL.md` の冒頭に「Critical Rules」セクションを新設し、ロード後の「三点検証（Triangulation）」を絶対的な義務として定義する。

## 実装内容詳細
### 1. `skills/github-investigator/SKILL.md` の更新
- **Frontmatter**:
    - `description` を「いつ使うか」「何と戦うか」にフォーカスした内容に刷新。
- **Body**:
    - `## Critical Rules` セクションを追加。
    - 「主観的ノイズの排除」と「物理的証拠（コード）の優先」を命令として記述。

## ゴール
- [ ] GitHub 関連の問い（例: 「GitHub でアプデ検討されているか？」）に対して、エージェントが迷わず `github-investigator` スキルを選択・ロードする。
- [ ] スキルロード後、エージェントがラベルの確認、メンテナの特定、コードの検証というステップを、省略せずに実行する。
- [ ] 報告内容が「主観的な Issue の要約」ではなく、「客観的な事実認定レポート」に進化している。

## Appendix: 技術的選定理由 (Why/Why Not)
- **Why**: スキルはエージェントの「セマンティック・ルーター」によって選択されるため、`description` は単なるテキストではなく、ルーターへの入力パラメータ（ベクトル）として設計されるべきである。
- **Why Not**: サブエージェント化も検討したが、GitHub 調査は開発フローの中で頻繁に発生するため、メインエージェントがスキルとして「思考の道具」を使い分ける方が、コンテキストの切り替えコストを抑えつつ高い精度を維持できる。
