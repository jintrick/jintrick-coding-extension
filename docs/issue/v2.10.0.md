# Issue: issue-crafter の自律化（Skill化）および動的テンプレート・同期スクリプトの導入

## 背景と問題点
1. **外部依存**: `issue-crafter` がプロジェクト内の `docs/issue/TEMPLATE.md` に依存しているため、拡張機能単体での配布（アトミックな動作）が困難である。
2. **ハルシネーション**: Issue フロントマター（ID, status, created, type）の更新を LLM の生成に委ねているため、日付の誤りやステータスの更新漏れ、採番ミスが多発している。
3. **物理的不整合**: `fixed_commit` はコミット前に確定できない「未来の情報」であるため、ファイルへの直接記録は不整合の原因となる。

## 解決策
1. **外部依存の解消 (Skill へのアセット封入)**: `skills/issue-crafter/` を新設し、標準テンプレート（`TEMPLATE.md`）と動的生成スクリプト（`generate-template.cjs`）を拡張機能内に同梱する。これにより拡張機能単体での配布・自律動作を可能にする。
2. **ハルシネーションの排除 (物理的証拠に基づく自動解決)**: LLMの推論を排除し、以下のロジックで各フロントマターを物理的証拠に基づき自動解決する。
    - **`id`**: 現在のGitブランチ名（例: `feat/v2.10.0` の `v2.10.0` 部分）を優先。未確定時は `package.json` のバージョンと `type` から推論・採番する。
    - **`created`**: スクリプト実行時のシステム日付、または Git で追跡中の場合は該当ファイルの初回コミット日付で上書きする。
    - **`status`**: 初期起草時はスクリプトが `drafting` を固定で出力する。その後のライフサイクル（`in-progress` や `completed` への遷移）は `issue-crafter` の責務から完全に切り離す。代わりに同期スクリプト (`tools/issue-sync.cjs`) が Markdown 内の DoD（未チェック項目 `[ ]` の有無）を検査し事後的に自動遷移させる仕組みを構築する（このスクリプトは将来的に別のエージェントやGitフックが実行する）。
    - **`type` の決定責務の移行**: `type` は「どのような要求か」を表すものであるため、決定の責務を `issue-crafter` の推論から、「ブランチを作成するエージェント（メインまたはgit-expert）」の物理的な命名（`[type]/[ID]`）へ移行する。`issue-crafter` はブランチ名（プレフィックス）という物理的証拠を `type` として適用する。
3. **物理的不整合の解消 (未来の情報の廃止と命名規則の強制)**: 未来の情報である `fixed_commit` フィールドを廃止する。代わりに、エージェント間に `[type]/[ID]` 形式のブランチ命名規則を強制し、Git のブランチ名をコードと Issue を紐づける物理的証拠（Ground Truth）とする。

## 実装内容詳細
1. **`skills/issue-crafter/` の構築**:
    - `SKILL.md`: テンプレート提供スキルの定義。
    - `references/TEMPLATE.md`: 標準テンプレートの Source of Truth（`fixed_commit` 廃止）。
    - `scripts/generate-template.cjs`: システム日付、`git branch`、`package.json` から情報を収集し、`id`, `created`, `type` を埋めた Markdown を出力する。`type` は Git のブランチプレフィックスから取得し、ブランチが存在しない初期状態の場合は一時的なプレースホルダーとして `[TYPE]` を出力する。
2. **`agents/issue-crafter.md` の更新**:
    - ワークフロー冒頭に「`issue-crafter` スキルを起動し、生成スクリプトを実行して物理的な事実が埋め込まれた最新のテンプレートを取得せよ」という指示を追記する。
    - `type` の自律的推論を撤廃し、スクリプトが提供する物理的証拠（ブランチ名等）を値として適用するよう指示を修正する。
    - 命名規則 `[type]/[ID]`（例: `feat/v2.10.0`）に沿ったブランチ名を提案するように指示を修正する。
3. **`agents/git-expert.md` の更新**:
    - ブランチ作成時、`[type]/[ID]` 形式を遵守し、この命名行為自体が `type` の決定（事実化）であることを拘束条件に追加する。
4. **`tools/issue-sync.cjs` の新規作成**:
    - Markdown 内の物理的証拠（DoD のチェック状態、Git 履歴、ブランチ名）に基づき、事後的にフロントマターの各項目（ID, Created, Status, Type）を前述の解決策のロジックに従って自動修正・同期する。

## ゴール
- `issue-crafter` が親エージェントからの最小限の指示（Intent）のみで、物理的な事実に基づいた不整合のない Issue を自律的に生成できる。
- フロントマターが物理的事実（Git/DoD）と一致し、常に最新の事実が維持される。

## Appendix: 技術的選定理由 (Why/Why Not)
- **Why: 自律化（推論＋物理矯正）**: 親エージェントが JSON 等で細かく指定するのではなく、子が「意味（Intent）から推論」し「物理（Script）で事実を固定」することで、トークン効率と正確性を両立させるため。
- **Why: prompt_crafter スキルに封入しなかった理由**: 汎用的な設計原則と、特定の Issue 形式という具体的ドメインの知識を分離し、メンテナンス性を確保するため。
- **Why: アセットをスキル（Skill）に封入した理由**: サブエージェントが拡張機能内のファイルを読み取るための、Gemini CLI における標準的な権限獲得手段であるため。
- **Why: fixed_commit の廃止**: 未来の情報（ハッシュ）をコミット前に書くことは論理的に不可能であり、不整合を招く。コードの特定は Issue ID とブランチ名によって一意に行えるため。
- **Why: [type]/[ID] 命名規則の強制**: ブランチ名というGitの物理的証拠を ID と Type の根拠（Ground Truth）にすることで、スクリプトによる自動矯正の信頼性を高めるため。
