# Issue: issue-crafter の自律化（Skill化）および動的テンプレート・同期スクリプトの導入

## 背景と問題点
1. **外部依存**: `issue-crafter` がプロジェクト内の `docs/issue/TEMPLATE.md` に依存しているため、拡張機能単体での配布（アトミックな動作）が困難である。
2. **ハルシネーション**: Issue フロントマター（ID, status, created, type）の更新を LLM の生成に委ねているため、日付の誤りやステータスの更新漏れ、採番ミスが多発している。
3. **物理的不整合**: `fixed_commit` はコミット前に確定できない「未来の情報」であるため、ファイルへの直接記録は不整合の原因となる。

## 解決策
1. **アセットの Skill 封入**: `skills/issue-crafter/` を新設し、標準テンプレート（`TEMPLATE.md`）と動的生成スクリプト（`generate-template.cjs`）を同梱する。
2. **自律的推論と物理的矯正**: エージェントがユーザーの意図から `type` を推論しつつ、スクリプトが収集した物理的な事実（システム日付、Git ブランチ、package.json）でフロントマターを強制的に固定（矯正）する仕組みを構築する。
3. **同期スクリプト (`tools/issue-sync.cjs`) の導入**: Markdown 内の「物理的証拠（DoD のチェック状態、Git 履歴、ブランチ名）」に基づき、事後的にフロントマターを確定的に自動修正する。
4. **エージェント間の命名規則同期**: `git-expert` および `issue-crafter` に共通のブランチ命名規則を強制し、自動判定の信頼性を 100% にする。

## 実装内容詳細
1. **`skills/issue-crafter/` の構築**:
    - `SKILL.md`: テンプレート提供スキルの定義。
    - `references/TEMPLATE.md`: 標準テンプレートの Source of Truth（`fixed_commit` 廃止）。
    - `scripts/generate-template.cjs`: システム日付、`git branch`、`package.json` から情報を収集し、`id`, `created`, `type` を埋めた Markdown を出力する。ブランチ名に `feat/` 等のプレフィックスがある場合は、それを最優先の `type` として反映する。
2. **`agents/issue-crafter.md` の更新**:
    - ワークフロー冒頭に「`issue-crafter` スキルを起動し、生成スクリプトを実行して物理的な事実が埋め込まれた最新のテンプレートを取得せよ」という指示を追記する。
    - ユーザーの要求（Intent）から `type` を自律的に推論しつつ、スクリプトが提供する物理的証拠（ブランチ名等）がある場合はそれを優先するよう指示を修正する。
    - 命名規則 `[type]/[ID]`（例: `feat/v2.10.0`）に沿ったブランチ名を提案するように指示を修正する。
3. **`agents/git-expert.md` の更新**:
    - ブランチ作成時、必ず `[type]/[ID]` 形式を遵守することを拘束条件に追加する。
4. **`tools/issue-sync.cjs` の新規作成**:
    - **ID 同期**: `git branch` の `vX.Y.Z` 部分を最優先。未確定時は `package.json` + `type` (feat/refactor=Minor, fix/chore/docs=Patch) から推論する。
    - **Created 同期**: スクリプトが物理的に解決。新規ファイルなら実行日のシステム日付、追跡中なら `git log` の初回コミット日で強制上書きする。
    - **Status 同期**: Markdown 内の未チェック項目 `[ ]` が 0 個なら `completed`、それ以外は `in-progress`（Git 未コミットなら `drafting`）へ自動遷移させる。
    - **Type 同期**: ブランチ名のプレフィックスを優先し、Issue 内の `type` を強制的に修正する。

## ゴール
- `issue-crafter` が親エージェントからの最小限の指示（Intent）のみで、物理的な事実に基づいた不整合のない Issue を自律的に生成できる。
- フロントマターが「物理的事実（Git/DoD）」と 100% 一致し、常に「正装」された状態が維持される。

## テスト
- `npm run build` を実行。
- `issue-crafter` を起動し、生成されたドラフトの `id` や `created` が現在の環境（ブランチ、日付）と一致していることを確認する。
- DoD をすべて埋めた状態で `issue-sync` を実行し、`status: completed` 等の各項目が物理的事実に基づき正確に更新されることを確認する。

## Appendix: 技術的選定理由 (Why/Why Not)
- **Why: 究極の自律化（推論＋物理矯正）**: 親エージェントが JSON 等で細かく指定するのではなく、子が「意味（Intent）から推論」し「物理（Script）で事実を固定」することで、トークン効率と正確性を両立させるため。
- **Why: prompt_crafter スキルに封入しなかった理由**: 汎用的な設計原則と、特定の Issue 形式という具体的ドメインの知識を分離し、メンテナンス性を確保するため。
- **Why: アセットをスキル（Skill）に封入した理由**: サブエージェントが拡張機能内のファイルを読み取るための、Gemini CLI における唯一の標準的な権限獲得手段であるため。
- **Why: fixed_commit の廃止**: 未来の情報（ハッシュ）をコミット前に書くことは論理的に不可能であり、不整合を招く。コードの特定は Issue ID とブランチ名によって一意に行えるため。
- **Why: [type]/[ID] 命名規則の強制**: ブランチ名という「Git の物理的証拠」を ID と Type の決定的な根拠（Ground Truth）にすることで、スクリプトによる自動矯正の信頼性を 100% に高めるため。
