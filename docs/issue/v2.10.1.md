# Issue: issue-crafterの修正（事前にブランチを作成する責務を追加）

## 背景と問題点
現在、`issue-crafter` は Issue フロントマターの決定を「Git ブランチ名」という物理的証拠（Ground Truth）に依存している。しかし、Issue を起草するタイミングにおいて、該当のブランチがまだ作成されていないケースが多発している。
この場合、動的生成スクリプトはプレースホルダー（`[TYPE]`）を出力し、`issue-crafter` は単にブランチ名を「提案」するのみに留まり、根本的なハルシネーションの排除と自動解決の恩恵を受けられない「卵が先か鶏が先か」の状態になっている。

Issue を起草する行為と、その容れ物であるブランチを作成する行為は不可分であるべきだ。

## 解決策

「ブランチの作成（物理的証拠の確定）」を `issue-crafter` 自身のワークフローの最初に組み込む。

## 実装内容詳細
1. **`agents/issue-crafter.md` の更新**:
    - ワークフローを再編し、「スキルの起動」の次に「Type/ID の推論とブランチの作成（`git checkout -b [type]/[ID]`）」を義務付ける。
    - 必ずこの Git コマンドを実行した**後**に、`scripts/generate-template.cjs` を実行してテンプレートを取得するよう指示を変更する。
    - 「Type の適用」に関する冗長な分岐指示（`[TYPE]` の場合の推論など）を削除し、常にブランチ名（確定済みの物理的証拠）を絶対的な事実として適用するシンプルなフローに圧縮する。

## ゴール
- `issue-crafter` がユーザーの要求（Intent）から自律的にブランチを作成し、プレースホルダーを含まない完全な物理的事実（Ground Truth）に基づく Issue ドラフトを起草できるようになること。

## テスト

- [ ] エージェントが自律的に `fix/v2.10.1` ブランチを作成することを確認する。
- [ ] 生成されたドラフトのフロントマターがプレースホルダーなく、正しく解決されていることを確認する。

## Appendix: 技術的選定理由 (Why/Why Not)
- **Why: ブランチ作成責務の統合**: ブランチ名そのものが Issue の ID と Type を決定づけるシステムにおいて、起草前にブランチが存在しない状態は設計上の破綻であるため。起草者が「場所」も用意することで、依存関係の順序が正常化する。
