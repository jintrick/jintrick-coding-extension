## 概要 (Overview)
Windows環境において、`md.cjs` (Human Linter) が一時ファイルをエディタで開く際、エディタを完全に閉じるまで `write_file` や `replace` ツールの実行が完了しない（ブロックされる）問題が発生している。

## 再現手順 (Reproduction Steps)
1. Windows環境で `gemini-cli` を起動する。
2. マークダウンファイルに対して `write_file` または `replace` を実行する。
3. `md.cjs` が起動し、Notepad 等のエディタが開く。
4. エディタが開いている間、Gemini CLI のプロンプト（ツールの実行完了）が返ってこない。

## 原因分析 (Root Cause)
現在の `md.cjs` は `spawn(editor, [path], { detached: true, shell: true })` を使用している。Windows の `shell: true` (cmd.exe) 経由で GUI アプリを起動すると、`cmd.exe` が子プロセスの終了を待機し続け、`detached: true` が期待通りに機能していない。

## 修正案 (Proposed Fix)
Windows 環境では `cmd.exe /c start "" "editor" "path"` を使用するように `md.cjs` を修正する。`start` コマンドはGUIアプリを非同期で起動し、即座に呼び出し元へ制御を戻す。

## 修正内容 (Implementation Details)
当初は `spawn` や `exec` で直接 `start` コマンドを実行していたが、子プロセス（GUIエディタ）が親プロセス（Linter Hook）の標準入出力ハンドルを継承してしまい、エディタを閉じるまで Gemini CLI の受信が完了しない問題が解消されなかった。

最終的に、Windows においてプロセスを完全にデタッチする「黄金律」である **VBScript (WScript.Shell.Run)** を採用した。
- `wscript.exe` を経由してエディタを起動。
- `WshShell.Run` の第3引数に `False` (待機しない) を指定することで、GUIプロセスを親プロセスから完全に切り離して「放流」することに成功。
- これにより、エディタが開いた瞬間に Linter Hook が終了し、Gemini CLI に即座に制御が戻るようになった。

## 検証結果 (Verification Results)
1. `tests/exp/test_v1.26.0_vbs.md` を作成。
2. Windows 環境で Markpad (EDITOR) が起動。
3. エディタを閉じることなく、Gemini CLI のプロンプトが即座に返ってくることを確認。
4. `tests/exp/md_linter.log` に `VBS Launcher executed via wscript.` の記録を確認。
