# Issue: agy と gc の協調動作を担う agy-client スキルおよび MCP サーバーの実装

## 背景と問題点 (Why)

gc と agy を連携させた開発ワークフローにおいて、「計画策定 → 人間の承認 → 実装」のプロセスを標準入出力の直接制御など不安定な方法で行うと、状態の非同期化やパースエラーが発生するリスクがある。標準的かつ安全なプロトコルによる状態同期が不可欠である。

## 解決策 (What)

ファイルシステム（`.agents/sync_state_{request_id}.json`）をバックエンドとした stdio ベースの MCP サーバーを導入し、それを gc 側から操作するための単一統合スキル `agy-client` を実装する。

承認待ちは人間が関与するため、秒単位から時間単位まで待機時間が不定である。MCP ツールハンドラ内でレスポンスをブロックすると Node.js のイベントループ自体が停止し、MCP フレームワークが他のメッセージに応答できなくなる。そのため、**ツールは即座にリクエスト受付を返し、gc 側のポーリングで状態変化を検知する**設計を採用する。

## 実装内容詳細 (How)

### 1. MCP サーバー (`skills/agy-client/mcp/index.js`)

Node.js で stdio MCP サーバーを実装する。提供するツールは以下の2つ。

**`request_approval(phase, artifact_path)`**

- 呼び出し時、`request_id`（UUID v4）を生成する。
- `.agents/sync_state_{request_id}.json` に初期状態を書き込む。

  ```json
  {
    "request_id": "<uuid>",
    "status": "pending",
    "phase": "<phase>",
    "artifact": "<artifact_path>",
    "created_at": "<ISO8601>"
  }
  ```

- 即座に `{ "request_id": "<uuid>", "status": "pending" }` を返す（ブロックしない）。
- gc はこの `request_id` を使って以降のポーリングを行う。

  > **Note**: かつての設計ではハンドラ内で `fs.watch` により `approved`/`rejected` まで待機する方式を検討したが、MCP の stdio トランスポートはシングルスレッドで動作するため、ハンドラのブロックはフレームワーク全体の停止を招く。この設計は採用しない。

**`poll_status(request_id)`**

- `.agents/sync_state_{request_id}.json` を読み取り、現在の `status` と付随情報（`feedback` 等）を返す。
- gc はこのツールを一定間隔でループ呼び出しし、`approved` または `rejected` になるまで待機する。
- ファイルが存在しない場合は `{ "status": "not_found" }` を返す。

### 2. クライアントスクリプト (`skills/agy-client/scripts/client.cjs`)

以下の CLI サブコマンドを実装する。すべてのコマンドで `--request-id <uuid>` を必須引数とする。

| コマンド | 動作 |
|---|---|
| `status --request-id <uuid>` | 対象ファイルを読み取り、現在の状態と `artifact` パスを標準出力に表示する |
| `approve --request-id <uuid>` | `status` を `approved` に更新する |
| `reject --request-id <uuid> --feedback "<text>"` | `status` を `rejected` に更新し、`feedback` フィールドに文字列を書き込む |

状態ファイルへの書き込みは、競合状態を防ぐため排他ロック（`fs.openSync` + `O_EXCL` によるロックファイル方式、またはアトミックな rename 方式）を用いる。

### 3. スキル定義 (`skills/agy-client/SKILL.md`)

gc 向けに以下のワークフローを定義する。

1. `request_approval(phase, artifact_path)` を呼び出し、`request_id` を取得・保存する。
2. `poll_status(request_id)` を一定間隔（例: 30秒）でループ呼び出しする。
3. `status === "approved"` を受け取ったら実装フェーズに進む。
4. `status === "rejected"` を受け取ったら `feedback` を読み取り、計画を修正して再度 `request_approval` を呼び出す。

- ユーザーの承認・却下フローが安定して運用可能になる。

## Appendix: 技術的選定理由 (Why/Why Not)

**ファイルシステムをバックエンドにする理由**
stdio でプロセス間通信を行う場合、標準出力の直接パースではノイズが混入しやすい。ファイルシステムを中間層にすることで、MCP サーバー・クライアントスクリプト・gc の3者が疎結合に状態を参照できる。

**ポーリング方式を採用する理由**
`fs.watch` による変更通知は実装が単純だが、MCP ハンドラ内で使用すると非同期待機中もイベントループが Node.js の制御を離れないため、フレームワーク全体が応答不能になる。gc 側でポーリングする方式は責務が明確であり、MCP サーバーの実装をステートレスに保てる。

**`request_id` 単位でファイルを分割する理由**
単一の `sync_state.json` を複数フェーズで共有すると、並行する `request_approval` 呼び出しで書き込みが競合する。`request_id` をファイル名に含めることで名前空間を分離し、競合を構造的に防ぐ。
