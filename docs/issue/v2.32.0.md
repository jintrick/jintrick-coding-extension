# Issue: agy と gc の協調動作を担う agy-client スキルおよび MCP サーバーの実装

## 背景と問題点 (Why)

gc と agy を連携させた開発ワークフローにおいて、「計画策定 → 人間の承認 → 実装」のプロセスを標準入出力の直接制御など不安定な方法で行うと、状態の非同期化やパースエラーが発生するリスクがある。標準的かつ安全なプロトコルによる状態同期が不可欠である。

## 解決策 (What)

MCPサーバープロセス内に極小の **ローカル HTTP サーバー** を内包し、状態をオンメモリで管理するアーキテクチャを採用する。

承認待ちは人間が関与するため待機時間が不定である。MCP ツールハンドラ内でレスポンスをブロックすると Node.js のイベントループ自体が停止し、MCP フレームワークが他のメッセージに応答できなくなる。そのため、**ツールは即座にリクエスト受付を返して gc 側がポーリングを行う**方式とする。

同時に、人間の承認操作を行うクライアントスクリプト（`client.cjs`）は、ファイルシステムを直接操作するのではなく、MCPサーバーが公開するローカルAPI（REST）を叩いて状態を更新する。これにより、`jules-client` のようにステートレスで洗練されたクライアント構造を実現し、排他制御（ファイルロック）の複雑さを完全に排除する。

## 実装内容詳細 (How)

### 1. MCP サーバー (`skills/agy-client/mcp/index.js`)

Node.js で stdio MCP サーバーを実装する。プロセス起動時にローカルポート（例: `14321`）で HTTP サーバーを立ち上げ、状態をメモリ上の `Map` オブジェクトで一元管理する。

**【MCPツール提供（gc向け）】**
- **`request_approval(phase, artifact_path)`**:
  - `request_id`（UUID v4）を生成。
  - メモリ上の `Map` に `{ status: 'pending', phase, artifact, created_at }` を保存。
  - 即座に `{ "request_id": "<uuid>", "status": "pending" }` を返す（イベントループをブロックしない）。
- **`poll_status(request_id)`**:
  - メモリ上の `Map` から該当 ID の状態を即座に返す。存在しない場合は `not_found`。

**【HTTP API提供（client.cjs向け）】**
- `POST /approve`: JSONボディ `{ "request_id": "<uuid>" }` を受け取り、`Map` の状態を `approved` に更新。
- `POST /reject`: JSONボディ `{ "request_id": "<uuid>", "feedback": "<text>" }` を受け取り、状態を `rejected` とし `feedback` を保存。

### 2. クライアントスクリプト (`skills/agy-client/scripts/client.cjs`)

HTTP API を叩くステートレスな CLI サブコマンドを実装する。引数は `--request-id <uuid>` とする。

| コマンド | 動作 |
|---|---|
| `status --request-id <uuid>` | `GET /status/<uuid>` などを叩き、現在の状態を表示（必要に応じてAPI追加） |
| `approve --request-id <uuid>` | `POST http://localhost:14321/approve` を送信 |
| `reject --request-id <uuid> --feedback "<text>"` | `POST http://localhost:14321/reject` を送信 |

※クライアントスクリプト自体は `fs` モジュール等による状態管理を一切行わない。

### 3. スキル定義 (`skills/agy-client/SKILL.md`)

gc 向けに以下のワークフローを定義する。

1. `request_approval(phase, artifact_path)` を呼び出し、`request_id` を取得・保存する。
2. `poll_status(request_id)` を一定間隔（例: 30秒）でループ呼び出しする。
3. `status === "approved"` を受け取ったら実装フェーズに進む。
4. `status === "rejected"` を受け取ったら `feedback` を読み取り、計画を修正して再度 `request_approval` を呼び出す。

## Appendix: 技術的選定理由 (Why/Why Not)

**ファイルシステム（I/O）を排除した理由**
複数のプロセスからのファイル操作は `fs.openSync` によるロックなど煩雑な排他制御を伴い、競合バグの温床となる。MCPサーバー内にHTTPサーバーを同居させ、状態を単一プロセスのオンメモリで一元管理することで、これらの問題を根本から解決できる。

**組み込みHTTPサーバーとオンメモリ管理の採用**
`jules-client` スキルが REST API を介してステートレスに動作し、非常に成功している点に倣った。揮発性（プロセス再起動で状態が消える）というトレードオフはあるものの、短時間の承認フローにおいては「アーキテクチャのクリーンさ」と「I/Oバグの排除」のメリットが圧倒的に勝ると判断した。

**ポーリング方式を採用する理由**
`fs.watch` やロングポーリングを使用すると、MCP ハンドラ内で非同期待機中もイベントループが Node.js の制御を離れないため、フレームワーク全体が応答不能になる。gc 側で定周期ポーリングする方式は、MCPサーバーを完全に非同期・ノンブロッキングに保つための最適解である。
