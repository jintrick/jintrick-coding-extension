# Issue: code-reviewer への自省プロセスの追加

## 背景と問題点
現行の `code-reviewer` は「客観的かつ厳格なレビュー」を重視するあまり、ローカルツールや小規模なスクリプトに対しても、大規模サーバーサイドと同等の堅牢性を要求し、現実的には発生し得ない、あるいは発生しても影響が軽微なエッジケースに対して過剰な指摘を行い、結果としてオーバーエンジニアリングを誘発している。

## 解決策
`agents/code-reviewer.md` のプロンプトを修正し、プロジェクトの規模や用途（コンテキスト）に応じた「指摘のフィルタリング・ロジック（自省プロセス）」を導入する。

## 実装内容詳細
プロンプト本文に「自省と指摘の選別基準」セクションを新設し、以下のロジックを組み込む：

1. **プロジェクト背景の分析**: `read_file` 等を用いて `package.json` や `GEMINI.md` を確認し、そのプロジェクトが「ローカルツール」なのか「基幹システム」なのか等のクリティカリティを分析させる。
2. **コスト・リスク評価の強制**: 指摘を確定させる前に、「その事象が発生する確率 × 発生時の被害」と「修正に必要なコードの複雑化・維持コスト」を比較させ、リスクが極めて低く修正コストが上回る場合は指摘を抑制させる。
3. **指摘のレベル分け**: 全ての指摘に対し、以下のラベル付けを強制する。
   - `[Critical]`: プロジェクト規約違反、または現実的なデータでの致命的バグ。
   - `[Recommendation]`: コード品質向上やエッジケースへの備え。
   小規模プロジェクトやローカルツールでは、`[Recommendation]` の提示を最小限に留めるよう指示する。
4. **注意**: 他のサブエージェント呼び出しは行わず、あくまで指示文の強化による論理的なフィルタリングで対応する。

## ゴール
- `code-reviewer` が、プロジェクトのコンテキスト（規模・用途）に適した実利的な指摘を行うようになる。
- ローカルツールや小規模プロジェクトにおいて、過剰なエラーハンドリングの強要が抑制され、「Fail Fast」という設計方針が正当に評価されるようになる。
- オーバーエンジニアリングを誘発する「念のため」の指摘が減少する。
