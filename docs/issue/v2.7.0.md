# Issue: OSS 調査の信頼性を担保する github-investigator スキルの実装

## 概要
`gh` コマンドを使用して GitHub 上の Issue、PR、ソースコードを調査する際、主観的な意見（ノイズ）を排除し、メンテナの合意とコードレベルの真実を特定するための厳格な調査ワークフローを定義するスキル `github-investigator` を作成する。

## 背景と問題点
現状、GitHub 上の調査において、一部のユーザーによる主観的な不満（Issue）をそのまま「公式の仕様」や「バグ」として誤認するリスクがある。特に、以下の点が不十分である：
1.  **ラベルの軽視**: `need-triage` などのステータスを確認せず、未検証の情報を鵜呑みにする。
2.  **発言者の属性無視**: 一般ユーザーとリポジトリメンテナの発言を区別していない。
3.  **コメントの未踏破**: 議論の末に却下された、あるいは修正された経緯を見落とす。
4.  **コードとの乖離**: Claim（主張）が最新の `main` ブランチのコードと一致するかを物理的に検証していない。

## 解決策
`github-investigator` スキルを導入し、以下の「三点検証（Triangulation）」を強制する。
1.  **Metadata Check**: ラベル、ステータス、メンテナ属性の確認。
2.  **Consensus Check**: コメント全文のスキャンとメンテナの最終判断の特定。
3.  **Code Evidence Check**: Claim を裏付けるコードの実在確認（`gh search code` / `gh api`）。

## 実装内容詳細
1.  **`skills/github-investigator/SKILL.md`**:
    - OSS 調査の「鉄則」を定義。
    - `gh issue view --comments` の必須化とパース手順。
    - `gh search code` による Claim の物理検証フロー。
2.  **`references/consensus_rules.md`**:
    - 信頼できるラベル（`accepted`, `confirmed`）と警戒すべきラベル（`need-triage`, `discussion`）のリスト。
    - メンテナを特定する方法。
3.  **ビルド設定の更新**:
    - `tools/build.cjs` により、新しいスキルとして `dist/` へ反映。

## ゴール
- [ ] スキル `github-investigator` が `/skills list` に表示される。
- [ ] スキル適用時に、モデルが単なる検索結果の要約ではなく、ラベルの状態やメンテナの意向、コード上の証拠を含めた「多角的レポート」を出力するようになる。
- [ ] 誤った情報源（例: 未検証のIssue）に基づいた断定的な報告がなくなる。

## Appendix: 技術的選定理由 (Why/Why Not)
- **Why**: `gh` は強力だが、LLM はその出力を文字通りに解釈しすぎる傾向がある。プロンプトエンジニアリング（Skill）によって「懐疑的かつ論理的な分析者」としてのペルソナを強制することが、最も低コストで効果的な改善策である。
- **Why Not**: 独自に `gh` のラッパースクリプトを書く案も検討したが、GitHub の UI や API は頻繁に変更されるため、公式の `gh` コマンドの出力を「どう読むか」という思考プロセスの強化（Skill）に留めるのが保守性の面で有利である。
