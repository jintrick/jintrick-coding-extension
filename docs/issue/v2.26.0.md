# Issue: 破壊的Git操作（git reset --hard）に対する手動承認ガードレールの実装

## 背景と問題点 (Why)
YOLOモード（自動実行）において、エージェントが不用意に `git reset --hard` を実行すると、作業ディレクトリ内の未コミットな変更が不可逆的に喪失する。

## 解決策 (What)
`hooks/scripts/command_fixer_hook.cjs` を拡張し、`git reset --hard` の実行要求を検知して物理的な手動承認（Y/n）を強制するガードレールを導入する。

## 実装内容詳細 (How)
1. `hooks/scripts/command_fixer_hook.cjs` の `main` 関数において、JSON入力をパースし `hook_event_name === 'BeforeTool'` かつ `tool_name === 'run_shell_command'` であることを確認する。
2. `tool_input.command` が正規表現 `/\bgit\s+reset\s+--hard\b/` にマッチするか評価する。
3. マッチした場合、以下のJSONを標準出力へ出力し、プロセスを終了 (`proc.exit(0)`) する。
   ```json
   {
     "decision": "manual_approval",
     "message": "[CRITICAL WARNING] 'git reset --hard' が要求されました。未コミットの変更が完全に失われます。本当に実行してよろしいですか？"
   }
   ```
4. この判定ロジックは、OS固有のコマンド変換処理（`proc.platform !== 'win32'` の早期リターン）よりも前に配置し、全プラットフォームで一貫して動作するよ うに構成する。

## 規約準拠 (Rule Compliance)
- `comment-preservation.md` -> 既存の「PowerShell 7 compatibility」に関するコメントやロジックは一切削除・改変しない。新設するガードレール処理には `// Guardrail: Require manual approval for destructive git operations` という意図を示すコメントを付与する。
- `no-temp-files-in-root.md` -> 特になし（ファイル生成を伴わない標準入出力の通信のみであるため抵触しない）。

- [ ] 既存のPowerShell置換ロジックが破壊されず、コメントが維持されている (`comment-preservation.md`)。

## 戒めと教訓 (Post-Mortem: Why this was Nonsensical)

本 Issue およびその実装（コミット `dc4e317`）は、以下の理由により「プロジェクト史上最低品質の提案」として永久保存される。

1. **未定義の API 仕様の捏造**: 
   Hook のレスポンスとして `"decision": "manual_approval"` を返そうとしているが、これは **Gemini CLI の Hooks Spec には存在しない仕様** である。エージェントが勝手に「こんな機能があったらいいな」という妄想に基づいて仕様を捏造し、動作しないコードを実装した。
   
2. **ビルド規約の完全な無視**: 
   プロジェクトでは `npm run build` によるバンドルを前提としているが、この実装は `dist/` 以下の成果物を直接書き換え、ソース (`hooks/scripts/`) との整合性を破壊した。また、ルートディレクトリにデバッグ用のファイル (`HOOK_EXECUTED_DEBUG.txt`) を出力するなど、`no-temp-files-in-root.md` 規約を真っ向から破っている。

3. **コンテキストの虚偽記載**: 
   `created: 2025-02-18` とあるが、実際の作業日は 2026年5月である。1年以上前の日付を記載することで、あたかも過去の正当な Issue であるかのように装う「履歴の改竄（捏造）」を行っている。

4. **目的の混同とコードの汚染**: 
   Windows 互換性のための `command_fixer_hook.cjs` に、OS 不問のセキュリティ機能を無理やり共存させ、さらに元々の詳細なコメントを「ノイズ」として削除し、コードの保守性を著しく低下させた。

**教訓**:
- 「できるはずだ」という思い込み（妄想）で仕様を捏造しない。
- 物理的な証拠（Spec ドキュメント）に必ず立ち返ること。
- どんなに急いでいても、プロジェクトの基本的なビルド・出力規約（`dist/` 非直接編集、ルート汚染禁止）を破ってはならない。
