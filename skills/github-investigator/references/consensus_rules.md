# OSS Consensus Verification Rules

GitHub での調査において、情報の信憑性を評価するための基準です。

## 1. ラベル (Labels) の信頼度評価

Issue や PR に付与されているラベルは、その情報の公式な「ステータス」を示します。

### 警戒すべきラベル（未確定情報）
- `status/need-triage` (要仕分け): 運営側がまだ内容を精査しておらず、事実かどうかも確定していない状態。**この状態の Issue に書かれた「バグ報告」や「仕様の批判」を事実として扱ってはならない。**
- `status/needs-info`: 報告者の情報が不足しており、調査が止まっている状態。
- `discussion` / `RFC`: コミュニティでのアイデア出しの段階。まだ実装の合意は得られていない。

### 信頼できるラベル（確定情報）
- `status/accepted` / `confirmed`: メンテナが問題を認識し、対応することを合意した状態。
- `priority/p0` ~ `p3`: 優先度が設定されており、バックログとして公式に積まれている状態。
- `kind/bug`: 公式にバグとして認定された状態。

### 却下された情報
- `status/wontfix` (対応しない): 仕様通りであるか、プロジェクトの方向性に合わないため却下された状態。
- `status/duplicate`: 既存の別の Issue に統合された状態。親 Issue を探しに行くこと。

## 2. 発言者の属性判定 (Speaker Role)

コメントを読む際は、「誰が」発言しているかを常に確認せよ。

- **Member / Collaborator / Owner / Contributor**:
  プロジェクトのメンテナ側。彼らの発言は「仕様の説明」「今後のロードマップ」「却下の理由」を構成する「公式の事実」である。
- **Author (報告者)**:
  Issue の起票者。彼らの発言はあくまで「不満」や「要望」であり、「現在のシステムはこう動いている（はずだ）」という思い込みが含まれていることが多い。**裏付けなしに事実として採用してはならない。**
- **一般ユーザー**:
  「私も同じ問題に直面している」などの同調意見。重要度の指標にはなるが、技術的仕様のソースとしては弱い。

## 3. 合意（Consensus）の抽出方法

Issue のコメント欄をスクロールする際は、以下のパターンを探すこと。

1. **メンテナによる事実確認 (Fact-checking)**:
   - 「実際にはこの機能はこう動きます (Actually, the current behavior is...)」
   - これは、報告者の誤解を正す非常に価値の高い情報である。
2. **方針の決定 (Decision)**:
   - 「この機能は Phase 2 で実装します」
   - 「このアプローチは複雑すぎるため、別の方法をとります」
3. **ワークアラウンドの提示 (Workaround)**:
   - 「現状は、この設定ファイルを使うことで回避できます」
